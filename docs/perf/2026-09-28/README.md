# 성능 측정 결과 (2026-09-28)

명세 9장 / 목표 PER-RES-01: 지도 영역 조회 서버 처리 500ms 이내.
측정 절차와 스크립트는 [`backend/scripts/perf/README.md`](../../../backend/scripts/perf/README.md)에 있다.

## 결론

- **인덱스 적용 후(현재 V1 스키마) 모든 조회 API의 p95가 75ms 이하**로 목표 500ms를 만족한다.
- 인덱스가 없으면 **이력 API가 p50 761ms로 목표를 넘고**, 30분 집계 쿼리는 60초 안에 끝나지 않는다.
  효과가 가장 큰 인덱스는 `UNIQUE (charger_id, status_updated_at)`이다 (이력 1,333ms → 0.1ms, 집계 시간 초과 → 137ms).
- `idx_station_lat_lng`는 지도 검색을 빠르게 하지 못했다 (아래 "발견한 점" 1).

## 발견한 점

1. **지도 검색은 위경도 인덱스보다 "서비스 대상" 조건이 더 좁다.** 화면 안 충전소는 1,163곳인데 그중 서비스 대상은 5곳이다.
   인덱스가 있으면 플래너가 1,163곳을 먼저 읽고(12ms), 없으면 매핑 542건부터 PK로 찾아간다(1.9ms).
   둘 다 목표보다 훨씬 빨라 지금은 바꾸지 않는다. 서비스 대상이 크게 늘거나 충전소 수가 훨씬 많아지면 다시 잰다.
2. **이력 테이블 인덱스는 조회 API와 집계 모두의 전제다.** 이 인덱스 없이는 5분 수집·30분 집계 주기를 지킬 수 없다.
   UNIQUE 제약이 중복 적재 방지와 인덱스를 겸하므로 추가 인덱스는 필요 없다.
3. 검색·상세의 쿼리 수는 결과 건수와 관계없이 3회로 고정이다 (N+1 없음, 단계 5 테스트로 검증).

## 한계

- 운영 서버(EC2 t4g.small, 2 vCPU·2GB)가 아니라 개발 PC에서 쟀다. 운영 서버는 메모리가 작아 이력 테이블이 캐시에 덜 올라가므로 이력·집계가 더 느릴 수 있다.
- 데이터가 전국에 고르게 흩어져 있다. 실제로는 도시에 몰려 있어 도심 화면의 영역 검색이 더 많은 행을 읽을 수 있다.
- 순차 호출만 쟀고 동시 접속 부하는 재지 않았다. 캐시가 비어 있을 때(콜드 캐시)의 시간도 따로 재지 않았다.
