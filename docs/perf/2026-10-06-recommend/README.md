# 추천 API 성능 측정·개선 (2026-10-06)

대상: `GET /api/recommendations` (명세 9장 PER-RES-01 목표: 서버 처리 500ms 이내).
측정 절차와 스크립트는 [`backend/scripts/perf/README.md`](../../../backend/scripts/perf/README.md)의 "추천 API" 절에 있다.

## 결론

- 개선 전에도 목표(500ms)는 만족했다 (p95 28ms). 다만 응답시간의 대부분이 **과거 통계 조회(R4) 한 곳**에 몰려 있었다.
  이 조회는 이력이 쌓일수록, 후보 충전소가 많을수록 커지는 구조라서 미리 개선했다.
- 두 가지를 함께 적용해 **p50 20.9 → 9.1ms (−56%), p95 28.4 → 9.8ms (−65%), max 40.5 → 10.4ms (−74%)**.
  1. **커버링 인덱스** `(station_id, window_start) INCLUDE (available)` (V4): R4가 읽는 페이지 **6,338 → 149 (−98%)**, Index Only Scan
  2. **DB에서 미리 집계**: 앱으로 보내는 행 **20,145 → 210**. 4주치 구간을 가져와 자바에서 세던 것을, (충전소, 요일, 도착 슬롯 일치 여부) 단위로 SQL에서 센다
- **둘 중 하나만 하면 효과가 작거나 오히려 나빠진다** (아래 "발견한 점" 1).

## 측정 조건

| 항목 | 값 |
|---|---|
| 환경 | 개발 PC (Apple M4, 16GB), Docker PostgreSQL 17.11, 앱은 같은 PC에서 jar 실행 |
| 기본 데이터 | `generate_data.sql` (충전소 100,000 / 충전기 550,000 / 매핑 542, 이력 1일) |

| 저장 순서 | `occupancy_30m`은 실제 집계처럼 **구간 순서**로 쌓았다. 한 충전소의 행이 테이블 전체에 흩어진다 |
| 입력 | routeId=3, 노선 첫 휴게소에서 출발, remainingRangeKm=1000 → **후보 충전소 15곳**, 이력 조회 기간 4주 |
| 반복 | EXPLAIN은 워밍업 1회 후 1회, HTTP는 워밍업 3회 후 **100회** 순차 호출 |

## 발견한 점

1. **집계만 바꾸면 더 느려진다 (상태 2: p50 28.6ms).** 인덱스가 없으면 집계 쿼리가 충전소마다 기존 UNIQUE 인덱스를 타고,
   `available`을 읽으려고 흩어진 테이블 페이지를 행마다 방문한다 (18,584 pages). 기존 쿼리는 Bitmap Heap Scan으로 페이지를 한 번씩만 읽어서(6,338 pages) 오히려 나았다.
   커버링 인덱스로 테이블 방문을 없앤 뒤에야 집계의 이점이 살아난다.
2. **EXPLAIN 시간만 보면 개선 후가 더 느려 보인다.** R4 1.33ms (인덱스만) vs R4b 6.89ms (개선 후). 그런데 API 응답은 17.9 → 9.1ms로 줄었다.
   개선 전에는 DB 밖 비용이 컸기 때문이다. 2만 행을 JDBC로 받아 객체로 만들고 자바에서 다시 세는 시간이 약 10ms였다.
   또 `EXPLAIN ANALYZE`는 행마다 시간을 재는 오버헤드가 있어 행이 많은 집계 노드에서 실제보다 크게 나온다. **최종 판단은 API 응답시간으로 했다.**
3. **처음 의심한 휴게소·IC 노선 인덱스(`rest_area.route_id`, `interchange.route_id`)는 효과가 없다.**
   테이블이 210행·659행이라 Seq Scan이 0.1ms 안에 끝난다. 추가하지 않았다.
4. 측정 데이터의 저장 순서를 실제와 맞췄다. 실제 집계는 30분마다 전체 충전소를 쓰므로 한 충전소의 행이 흩어진다.
   충전소 순서로 쌓으면 개선 전 쿼리가 실제보다 유리하게 측정된다.

## 남은 것

- 버퍼 캐시가 데워진(hit) 상태만 쟀다. 운영에서 캐시에 없으면 개선 전 6,338 pages(약 50MB)를 디스크에서 읽게 되므로 차이는 더 커진다.
- 동시 요청 부하(처리량)는 재지 않았다.
- `occupancy_30m` 보관 기간은 미정이라 12주로 가정했다. 조회는 최근 4주만 하므로 보관 기간이 늘어도 개선 후 비용은 거의 같다.
