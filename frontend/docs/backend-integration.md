# 백엔드 연결 기준

2번 작업에서는 현재 레포의 `StationQueryController`, `StationSearchCondition`, `RouteListResponse`, `StationSearchResponse`, `AccessPointView`, `CorsConfig`를 확인했습니다. 탐색에 쓰는 두 API를 해당 규격으로 구현했습니다. 운영 서버의 실제 데이터와의 통합 검증은 아직 수행하지 않았습니다. 다른 업무 API는 해당 작업에서 소스와 테스트를 확인해 연결합니다.

## 탐색 연결 규격

| 항목 | 연결 기준 |
|---|---|
| 노선 | `GET /api/routes`, `{ routes: [...] }` |
| 노선 검색 | `GET /api/stations?routeId=...&direction=...` |
| 지도 검색 | `minLat`, `minLng`, `maxLat`, `maxLng` 네 값 모두 전달 |
| 접근 필터 | `accessType=REST_AREA` 또는 `IC`, 전체일 때 생략 |
| 충전기 필터 | `chargerType` 코드가 요구하는 커넥터를 모두 가진 복합형 충전기도 검색 |
| 조회 상한 | 기본 100, 최대 500. `truncated=true`이면 추가 조회 또는 조건 축소 안내 |
| 상태 대수 | 급속충전기 전체 기준. `availableCount`·`chargingCount`에는 정상 분류만 포함하며 의심·고장·미확인은 각각 별도 대수 |
| 수집·변경 시각 | `statusCollectedAt`은 마지막 성공 수집, `latestStatusUpdatedAt`은 원천 상태 변경 시각. 오프셋 없는 LocalDateTime은 KST로 해석 |
| 인증 | 공개 GET에는 `credentials: omit` 사용 |

백엔드는 조회 상한으로 먼저 자른 뒤 `NORMAL → PARTIAL → ALL_ERROR` 신뢰도 순으로 정렬합니다. 위치를 확인한 경우 프론트에서 **조회된 후보 안에서** 신뢰도를 먼저 유지하고 같은 신뢰도 안에서 직선거리 순으로 재정렬합니다. 잘린 결과 전체에 대한 최단거리 정렬이나 실제 도로상의 전방 여부는 보장하지 않습니다. 지도와 목록 모두 같은 충전소 ID를 중복 표시하지 않으며, 여러 접근지점은 카드에 함께 요약합니다.

목적지에서 노선을 자동 계산하는 엔드포인트는 없으므로, 목적지 입력 후 노선·방향을 직접 선택합니다. 실제 경로·거리·ETA를 임의 생성하지 않습니다.

## 환경

- `VITE_APP_ENV=DEV`: 더미 데이터로 UI를 표시하고 헤더 우측에 DEV만 표시합니다.
- `VITE_APP_ENV=PRD`: `VITE_API_BASE_URL` 아래로 실제 요청을 전송합니다. DEV 표시를 숨기며 실패 시 더미 데이터로 바꾸지 않습니다.
- `.env.development`는 DEV, `.env.production`은 PRD입니다. Vite의 번들 모드와 앱 환경을 혼동하지 않도록 `config.environment`에서 데이터 경로와 표시를 함께 결정합니다.
- `VITE_API_TIMEOUT_MS`: 요청 제한 시간. 기본 10000ms입니다.
- `VITE_*`는 브라우저 번들에 포함됩니다. 비밀키·공공 API 인증키를 넣지 않습니다.

## 기능별 구현 방식

추천·비교 화면은 공개 `GET /api/recommendations`에 현재 위치 `lat`, `lng`, 카카오 장소 검색에서 선택한 목적지 `destLat`, `destLng`, 남은 주행거리 `remainingRangeKm`를 보냅니다. `chargerType`과 `limit`을 선택적으로 보내며, 노선·방향은 응답의 `route`에서 읽습니다. HTTP 200에서 `route: null`이면 자동 선택할 노선이 없는 경우이고, `route`가 있으며 `recommendations`가 비어 있으면 선택한 노선에 추천 후보가 없는 경우입니다.

응답의 `recommendations` 순위를 기본으로 유지하고, 사용자가 `가까운 순`을 선택하면 반환된 추천 후보를 `distanceKm` 기준으로 재정렬합니다. 같은 `restAreaId`와 방향에 속한 운영기관별 충전소는 한 묶음 안에 표시하되 충전소별 링크와 비교 선택은 유지합니다. `availabilityProbability`, `basis`, `eta`, `distanceKm`, `detourKm`, `busiId`, `orgName`을 검증해 표시하며, 이름이 없으면 운영기관 코드를 표시합니다. 마지막 상태 수집 시각은 응답 `route`의 노선 ID와 방향으로 `GET /api/stations?routeId=...&direction=...&limit=1`을 호출해 `statusCollectedAt`을 읽습니다. 이 조회가 실패해도 추천 결과는 유지하고 수집 시각만 확인 불가로 표시합니다.

현재 추천 API에는 **도착 시점 예상 빈 충전기 수**, 도착시각 입력, 예상 대기시간, 충전소별 고장·상태 신뢰도 필드가 없습니다. `availableCount`는 현재 이용 가능 대수이므로 도착 시점 예측 대수로 표시하지 않습니다. 백엔드는 정상 급속충전기가 최소 1대 있는 충전소만 추천 후보에 넣습니다. 일부 충전기만 고장난 충전소는 추천될 수 있으며, 추천 항목에서 충전기별 신뢰도를 확인할 수는 없습니다. M05 선택값도 현재 추천 결과에는 반영하지 않습니다.

4번 작업의 상세는 `GET /api/stations/{stationId}`, 충전기 상태 이력은 `GET /api/chargers/{chargerId}/history`에 연결합니다. 이력은 `[from, to)` 구간의 KST 로컬 시각을 보내며 기본 24시간, 최대 7일로 제한합니다. `nextCursor`가 있을 때만 다음 페이지를 요청합니다. 도착 시점 예측(M09)은 DEV에서 시연값을 표시하고 PRD에서는 상세 API로 확인한 현재 상태를 안내합니다.

혼잡 패턴(M10)은 `GET /api/stations/{stationId}/patterns?weeks=4`를 사용합니다. 응답의 요일·30분 칸 336개를 요일·3시간 칸으로 묶어 평균 점유율과 쾌적 비율에 각 30분 칸의 표본 수로 가중치를 적용합니다. 표본이 없는 칸은 데이터 없음으로 표시합니다. 응답의 KST 집계 기간, 유효·제외 구간 수, 쾌적 기준 사용률을 함께 표시합니다.

5번 작업의 운영기관은 `GET /api/operators`의 `operators` 배열에서 `busiId`, `name`, `stationCount`를 읽습니다. 선호 코드는 브라우저에만 저장하고 지도·경로·추천 응답의 `busiId`와 비교해 강조합니다. 즐겨찾기는 브라우저에 최대 20개 ID만 저장하고, 비어 있지 않을 때 `GET /api/stations/summaries?ids=1,2`를 호출합니다. `ACTIVE`, `CLOSED`, `NOT_FOUND`를 구분하며 서버 응답이 일부 누락되면 실패로 처리합니다. 추천 API는 선호 기관 목록을 입력받지 않으므로 추천 점수 자체는 개인화하지 않습니다.

6번 작업의 D01은 `GET /api/admin/collection-status?from=...&to=...` 응답을 검증해 가용률·회차 집계·누락 구간·디스크 상태를 표시합니다. 시각은 KST `LocalDateTime` 형식이며 조회 기간은 최대 31일입니다. API에 개별 회차 목록이나 예측 배치 상태가 없어 해당 영역은 집계와 연동 대기 상태로 표시합니다. 인증·인가가 아직 없으므로 PRD 운영 경로는 로그인 화면으로 이동합니다. 로그인 폼 입력은 서버로 전송하지 않고 인증되지 않은 접근은 차단합니다. DEV에서만 시연 데이터로 D00~D05를 탐색합니다. D02~D05의 통계·매핑·모델 관리 API는 계약 확정 후 연결합니다.

각 작업의 기능 폴더에서 화면 모델과 서비스 인터페이스를 정의하고, mock fixture와 실제 DTO 변환을 분리합니다. 응답을 제네릭 타입으로 지정해도 런타임 검증이 되지 않습니다. 실제 연동 시 스키마 검증 또는 명시적 파싱을 어댑터에 추가합니다.

```ts
const load = (signal: AbortSignal) => apiClient.request('백엔드에서 확정한 경로', {
  query: { page: 0 }, signal,
});
```

`path`에는 베이스 하위 경로를 주고 쿼리는 `query`에 전달합니다. 빈 값은 생략하고, 0과 false는 유지합니다. AbortSignal은 화면 이탈/재조회 시 취소에 사용합니다.

401·403·404·서버 오류·연결 오류·타임아웃·잘못된 JSON을 구분합니다. 401은 기능별 인증 컨텍스트에서 로그인으로 전환할 근거로 사용합니다. 공통 클라이언트가 임의로 라우트를 변경하거나 로그인 정보를 저장하지 않습니다.

공통 fetch의 기본값은 `credentials: include`이고 요청별로 변경할 수 있습니다. 탐색 API는 `omit`을 명시합니다. 운영자 인증은 6번 작업에서 실제 토큰/쿠키 규격, CSRF, CORS와 함께 검토합니다. 비밀번호나 토큰을 localStorage에 저장하는 코드는 없습니다. 서로 다른 도메인에 연결할 경우 백엔드 CORS와 쿠키 정책이 필요합니다.

## 백엔드 소스 확인 후 확정할 항목

1. 노선, 기관, 검색, 상세, 이력, 즐겨찾기 요약, 수집 현황 API의 URL과 실제 필드
2. 지도 bounds 형식, 방향 코드, 접근유형, 충전기 유형과 페이지네이션
3. 추천 API 입력·응답과 예측 없음/통계 대체의 의미
4. 타임스탬프 시간대, 갱신 지연 기준과 null의 의미
5. 운영자 로그인·실패 제한·세션 만료·권한과 관리 기능의 실제 지원 범위

## 요구사항 유지 규칙

- M05는 M06에서 여는 선택 화면. 기본 흐름은 M01 → M02 → M06.
- 기본 예측 시점은 30분. 15·45·60분은 서버 지원 확인 전 활성화하지 않습니다.
- 예측 없음 또는 산출 후 1시간 이상이면 0%나 한산함으로 표시하지 않습니다.
- `UNKNOWN` 충전 상태도 이용 가능으로 변환하지 않습니다.
- 현재 상태 갱신 시각과 예측 산출 시각을 구분합니다.
- 휴게소 방향 필터와 같은 노선 IC 포함 정책을 구분합니다. IC 거리 근사는 실제 길찾기가 아닙니다.
- 즐겨찾기 최대 20개와 선호 기관은 브라우저에 저장합니다.
- 선호 기관 목록의 서버 전달 여부는 분석서/설명서에 차이가 있으므로 추천 계약 확인 때 확정합니다. 기본 개인화 저장을 서버 사용자 계정으로 만들지 않습니다.
- 자동 수집·집계·예측 배치는 백엔드 책임입니다. 프론트는 상태를 표시하며 클라이언트 타이머로 수집 작업을 실행하지 않습니다.
